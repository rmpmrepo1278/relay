### R1
VERDICT: recommend
CONFIDENCE: high
AUTOFIX: YES
EVIDENCE: hermes_scheduler.py:412-419 — `def _load_jobs(self):` ... `if self.jobs_file.exists(): try: self.jobs = json.loads(...)`; hermes_scheduler.py:425-431 — `def _save_jobs(self): tmp = self.jobs_file.with_suffix('.tmp') ... os.replace(tmp, self.jobs_file)`; hermes_scheduler.py:443-452 — `def add_job(...)`: `for j in self.jobs: if j.get('name')==name: ... update`; hermes_scheduler.py:534-541 — `def remove_job`: `self.jobs = [j for j in self.jobs if j['name'] != name]`
PROBLEM: `self.jobs` is a bare `list[dict]` with untyped, stringly-typed fields (`name`, `schedule`, `command`, `enabled`, `last_run`, `next_run`). Every consumer re-derives shape via `.get()` chains (e.g. `j.get('enabled', True)`, `j.get('last_run')`), so a malformed entry silently yields default behavior instead of failing fast. The list is also the concurrency surface: `_load_jobs`/`_save_jobs` are called from both the daemon loop and CLI subcommands without a lock beyond the `.jobs.lock` file created elsewhere.
PROPOSAL: Introduce one `@dataclass Job` (or TypedDict) as the single owner of job shape, plus `Job.from_dict`/`to_dict`. Replace all `dict.get` accessors in this file with attribute access; validation happens once at load (skip+warn on malformed rows) instead of being scattered at each read site.
SCOPE: ~40 lines in hermes_scheduler.py only: dataclass + from_dict/to_dict + swap accessors at lines 412-560 region. No schema change — JSON on disk stays identical.
RISK: Low. Disk format unchanged; risk is a missed accessor causing AttributeError — mitigated by py_compile + running `--list` against the live jobs.json copy.
VALIDATION: `python3 -m py_compile /home/rohit/.hermes/scripts/hermes_scheduler.py && python3 /home/rohit/.hermes/scripts/hermes_scheduler.py --list`

PROBLEM: Every 30s tick re-parses every job's cron expression and re-scans the full jobs list to decide what's due, and `next_run` is stored but recomputed rather than trusted — O(jobs) work per tick with duplicated schedule logic between `_should_run` and wherever `next_run` is written after execution.
PROPOSAL: Maintain a min-heap `(next_run_ts, name)` updated only when a job runs or its definition changes; `_tick` pops due entries instead of scanning all jobs. Single owner of "when does this run next" logic.
SCOPE: hermes_scheduler.py only: replace linear scan in `_tick` with heapq keyed on persisted `next_run`; rebuild heap in `_load_jobs`.
RISK: Medium — heap can drift from disk edits made by other processes writing jobs.json directly; needs rebuild-on-mtime-change check. Behavior change to scheduling core warrants human review.
VALIDATION: `python3 -m py_compile /home/rohit/.hermes/scripts/hermes_scheduler.py && python3 /home/rohit/.hermes/scripts/hermes_scheduler.py --next-runs | head -20`
